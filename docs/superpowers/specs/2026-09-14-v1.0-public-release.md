# v1.0 public release design

## Goal

Publish the first GitHub release as a dependable ordinary-Chat context bridge: one long-lived Chat performs planning and authoring, while Codex owns live repository evidence, local adoption, computer actions, edits, and verification.

## Identity boundary

State schema 3 creates one random local scope key and derives an opaque HMAC scope id from:

- bridge id;
- normalized Chat reference;
- stable canonical workspace identity (root, repository, remote, and worktree).

ChatGPT conversation URLs are reduced to their stable conversation id. URL credentials, query parameters, and fragments are not persisted. The private scope key never appears in status, MCP, or support output. Requests and context queries carry the public scope id. A changed Chat or workspace produces `SCOPE_MISMATCH`.

Branch, HEAD, dirty-state, and checkpoint hashes remain separate per-round evidence and reuse guards. Their routine changes do not silently rotate the long-lived Chat scope.

Replacing a Chat is a transaction. `preview-chat-migration` records the source scope, state revision, workspace, checkpoint, target Chat hash, transport, reason, expiry, and preview hash. `apply-chat-migration` succeeds only if the preview and every source anchor remain unchanged.

## State upgrade

Schema-v1 and schema-v2 state require explicit `migrate-state`. Migration runs under the bridge lease and performs these steps:

1. Parse and recognize the entire source state.
2. Build and validate schema-v3 state in memory.
3. Save the exact original bytes in `backups/`.
4. Re-read the backup and verify its SHA-256 hash.
5. Append migration provenance and the new state snapshot to the journal.
6. Atomically replace `state.json`.
7. Re-read and validate the published state.

Migration records source and target schemas, time, source hash, backup name, and any abandoned in-flight round. Re-running migration on valid schema-v3 state is byte-stable.

## Context and token contract

Every prepared outgoing request has a sidecar `context-manifest.json`. Each possible source is marked `included` or `skipped`, and includes a source hash, local approximate token count, and reuse state. Mediated context responses add the same manifest with `redacted` and `truncated` dispositions.

The manifest is local accounting metadata. It is not provider billing and is not added to the normal Chat packet. Stable protocol instructions remain a one-time bootstrap. MCP status and health accept `since_revision`; an unchanged bridge returns only status, revision, and `unchanged: true`.

## Setup contract

`setup.mjs` changes project-local `.codex/config.toml` only. Preview creates a hash-bound plan containing the current config hash, proposed config hash, canonical workspace, Skill location, and exact target content. Apply rejects a changed plan or a config that changed after preview. Existing configs are backed up before atomic replacement.

The managed TOML block is marked and idempotent. An unmarked table with the same MCP server name fails with `SETUP_CONFLICT`. Removal deletes only the managed block and preserves runtime context.

## Diagnostic privacy

The public support bundle includes package/runtime versions, pass/fail check ids, source commit/state, state schema and revision, lifecycle status, public scope id, workspace fingerprint, transport, round, phase, and last outcome.

It excludes prompts, responses, source, filenames, filesystem paths, Chat references or titles, account data, cookies, credentials, and private scope keys.

## Release contract

`release-manifest.json` declares the version, state/context schemas, Node range, deterministic timestamp policy, included roots, exclusions, and validation commands. `build-release.mjs`:

- inventories every shipped source file with bytes and SHA-256;
- records the source commit and whether it came from a clean tree;
- records zero runtime dependencies;
- uses sorted paths, stored ZIP entries, and a fixed DOS timestamp;
- writes the ZIP, external `BUILD-MANIFEST.json`, and `SHA256SUMS`;
- can build twice and require byte equality;
- can refuse a non-clean release with `--require-clean`.

CI must run on Windows, macOS, and Linux. The release gate tests the ZIP structure and runs Doctor from an extracted archive. Publication still requires a clean committed tree and explicit user authorization.

## Recovery and failure codes

The public codes are:

| Code | Meaning | Safe next action |
|---|---|---|
| `SCOPE_MISMATCH` | Chat, bridge, request, or workspace identity differs | Inspect state and explicitly migrate or restore the intended scope |
| `STATE_CONFLICT` | State changed after the caller read or previewed it | Reload and rebuild the operation |
| `BRIDGE_BUSY` | A live writer owns the lease | Wait for that operation; never remove a live lease |
| `MIGRATION_REQUIRED` | State or migration input cannot be safely advanced | Inspect the backup/journal and reconcile before new work |
| `SETUP_CONFLICT` | Setup plan or project config changed | Regenerate and review the plan |
| `UNCERTAIN_DELIVERY` | Chat send/result state is not provable | Read the bound Chat and reconcile; never resend automatically |
| `BASE_CHANGED` | An artifact base no longer matches the workspace | Reopen the file and request or construct a new artifact |

While recovery is required, only inspection and explicit reconciliation are allowed. A failure never authorizes a new Chat send, local write, command, or external action.

If the most recent round was prematurely marked complete but its Browser Copy bytes cannot be verified, `invalidate-completed` requires the observed state revision and SHA-256 of a prior checkpoint stored in the same runtime. It preserves the attempted round and artifacts in the private journal, marks the result unadopted, restores the prior verified checkpoint as the active one, and pauses the bridge. It does not send or retry.

## Acceptance

- Existing v0.1-v0.9 tests remain green after deliberate protocol fixture updates.
- Scope tampering and cross-scope context reads fail closed.
- v2 migration keeps an exact verified backup and is idempotent.
- Chat and setup preview/apply flows reject stale input.
- Request and response manifests cover included, skipped, redacted, and truncated data.
- Revision reads return a compact unchanged response.
- Public support output contains none of its test Chat reference, title, workspace path, or private scope key.
- Two release builds are byte-identical.
- Doctor passes from the extracted archive.
- Full verification, release Doctor, diff checks, and Skill validation pass before publication.
