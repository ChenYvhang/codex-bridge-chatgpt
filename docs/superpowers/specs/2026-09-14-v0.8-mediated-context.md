# v0.8 Mediated Context Design

## Goal

Reduce context transfer toward sub-kilobyte control messages while preserving the bridge's zero-service default and local authority.

## Context request

A context request is bound to `bridge_id` and the active round. Supported operations are:

- `read_file`: one workspace-relative text file and a bounded line range;
- `search`: literal workspace search with bounded matches;
- `git_diff`: a bounded staged, unstaged, or HEAD diff, optionally scoped to one safe path;
- `latest_receipt`: the latest hash-verified execution summary.

Every operation has a request id. Unknown fields and operations fail closed.

## Security

- Canonical real paths must remain inside the bound workspace.
- Symlink escapes, absolute paths, NUL input, protected directories, credential filenames, binary files, and oversized reads are denied.
- Custom `.codexbridgeignore` entries add deny patterns.
- Returned content receives a likely-secret scan. A sensitive result becomes a structured denial; its content is never included.
- Responses contain only workspace-relative paths and content hashes.
- The whole response has a 2,000 approximate-token default budget and a 2,500 hard ceiling.

## Dry run

`bridge dry-run --spec <handoff.json>` performs the same workspace, checkpoint, compaction, validation, and budget checks as `start` without allocating a round or writing an exchange. It reports tokens by context-delta source.

## Delivery

`bridge provide-context --request <request.json> --output <response.json>` prepares the response locally. It does not send. Existing one-send transport and result adoption rules still apply.

## Future adapter

The request/response contract is transport-neutral. A later optional MCP transport may expose the same operations after workspace-bound authorization, without changing Chat-facing semantics.
