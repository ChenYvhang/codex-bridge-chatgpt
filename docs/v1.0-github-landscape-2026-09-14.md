# v1.0 GitHub landscape and launch direction

Date: 2026-09-14

## Executive finding

The strongest v1.0 is not the bridge with the largest remote tool surface. It is the bridge a user can install, understand, resume, audit, and remove without exposing a local execution service to the internet.

The current project already has a distinctive foundation: an ordinary ChatGPT Chat remains the long-lived planner and writer; Codex keeps local execution authority; only bounded, sanitized context crosses the boundary; accepted results are bound to local state and receipts; and the default path requires no daemon, OAuth server, or public tunnel. v0.8 added mediated pull requests and source-level token budgets. v0.9 added a local read-only STDIO MCP surface, crash-safe leases, and optimistic state revisions.

The peer audit changes the v1.0 priority. The public release should harden continuity, setup, diagnostics, state upgrades, and release provenance before adding a remote ChatGPT Developer Mode connector. A remote connector can be a later opt-in adapter built on the same context contract.

## Method

The review used GitHub search to find projects matching combinations of ChatGPT, Codex, MCP, local bridge, persistent session, context handoff, and Developer Mode. Marketing-only wrappers, generic API proxies, and unrelated Claude-to-Codex callers were deprioritized.

For each selected project, the repository was cloned, fixed to the commit below, and reviewed at source level. The review focused on:

- Chat and workspace identity;
- durable context and session recovery;
- path, secret, authorization, and execution boundaries;
- long-running jobs, approvals, cancellation, and concurrency;
- context size and result shaping;
- onboarding, diagnostics, tests, upgrades, and release governance.

The earlier source audit of Oracle and Codex with ChatGPT is incorporated rather than repeated. Repository claims are treated as product descriptions; implementation claims below come from reviewed source.

## Source findings

### CodexBridge

`src/guard.ts` and `src/policy.ts` implement canonical path containment, blocked patterns, and explicit allow/ask/deny decisions with risk categories. `src/changeSet.ts` uses expected base hashes, preview/apply phases, and a best-effort rollback record. `src/journal.ts` keeps a structured JSONL operation journal. `src/proContext.ts` builds bounded context bundles that report important files, changes, instruction files, skipped entries, truncation, and redaction.

Its best product idea is the complete first-run path: setup, tunnel selection, stable profile, health checks, copied connector URL, compact tool cards, and a public launch checklist. Its main mismatch with our v1.0 is the wide remote surface. File writes and shell tools are reachable through a public connector, and common configurations put a secret token in the URL. That can be acceptable for an explicit connector product, but it is a weaker default for an ordinary-Chat context bridge.

Borrow:

- setup as a guided transaction with a preview;
- a context manifest listing included, skipped, redacted, and truncated sources;
- operation history expressed in user terms;
- explicit task phases from brief through plan, preview, approval, apply, verify, and report;
- public readiness, security, contribution, and troubleshooting checklists.

Avoid:

- a broad remote write or shell surface in the default edition;
- query-string credentials;
- requiring a tunnel to obtain basic value.

### Codex MCP Bridge for ChatGPT

This is the most mature operational implementation in the sample. `scopeResolver.ts`, `threadConnections.ts`, and `sessionRegistry.ts` derive an opaque conversation scope, prevent cross-scope reuse, and make thread adoption explicit. Raw host subjects and organization identifiers are not retained as routing keys. The state subsystem uses SQLite schema versioning, migration locks, preflight checks, backups, integrity checks, and migration provenance. Job events and displayed results have retention budgets. The release system defines a machine-readable manifest, exact artifacts, hashes, migration catalogs, candidate/stable stages, compatibility checks, and promotion rules. The audited repository had 121 test files.

Borrow:

- opaque, scoped ownership for Chat, workspace, and local session mappings;
- explicit adoption when a session changes owner or scope;
- state migration preflight, backup, integrity check, and provenance;
- monotonic revisions and unchanged responses for cheap polling;
- release manifests, exact-commit gates, reproducible archives, and stable promotion from a verified candidate;
- a documented Codex protocol compatibility matrix.

Avoid:

- importing the complete SQLite, macOS UI, remote service, and release-candidate machinery into a small dependency-free skill;
- making App Server compatibility the only way to use the bridge.

### DeepCog Codex GPT Bridge

This project demonstrates a small, understandable Streamable HTTP bridge. It restricts working directories to canonical allowed roots, defaults to read-only, requires an explicit write enable, refuses to expose danger-full-access as a ChatGPT tool option, scans sensitive filenames, and returns a job id when Codex exceeds a fast-return deadline. It also shows the difference between ChatGPT web access and the paid Responses API in the reverse direction.

The session registry is memory-only, expires after six hours, and is not scoped to a Chat identity. Jobs are also memory-only. Authorization compares the Bearer header directly. Its simplicity is valuable, but it does not provide the continuity or recovery required by this project.

Borrow:

- short tool names and a small status/read/run/reply/job-status mental model;
- fast return for long work;
- an explicit explanation that ChatGPT web quota and API billing are different products.

Avoid:

- presenting an API call as access to an ordinary ChatGPT Chat;
- in-memory session ownership for a continuity product;
- scanning an entire workspace for sensitive filenames before every round.

### Dalomeve Codex ChatGPT Bridge

This implementation has a clear grant model: each canonical path can independently allow read, write, and execution. Restricted mode denies sensitive path names; configuration and session metadata are persisted with owner-only permissions where the platform supports them. It also treats a stable tunnel and a verified `bridge_status` or `list_grants` call as part of installation rather than an optional afterthought. A delegate profile reduces the visible tool surface.

Two choices should not be carried into our first release. The remote caller can expose `grant_path` and `set_bridge_mode` in the full profile, which lets the same trust domain request broader local authority. Session resolution accepts a global `latest`, which can select the wrong project or Chat. Full-delegate mode removes grant and sensitive-path protections entirely. A secret URL is convenient but still a credential that can leak through history, logs, or screenshots.

Borrow:

- human-readable named grants and separate read/write/execute capabilities for a future remote adapter;
- installation completion defined by an actual end-to-end status call;
- public-safe tunnel diagnostics that do not print secrets;
- a compact delegate profile.

Avoid:

- remote self-expansion of local grants;
- a global `latest` session alias;
- one switch that removes all path and sensitive-file controls.

### Codex from ChatGPT

This project uses the Codex App Server rather than parsing only final CLI text. `workspaces.ts` canonicalizes both the administrative root and requested workspace. `store.ts` validates the complete state schema, rejects ambiguous job and thread ids, and replaces the state atomically with restrictive permissions. `jobs.ts` tracks lifecycle, diff, files, commands, validation, warnings, approvals, activity, and monotonic revisions. `since_revision` and compact/standard/debug result levels reduce repeated output. App Server requests require the exact request id when multiple approvals coexist. An unexpected exit or uncertain timeout raises a recovery fence instead of silently starting more work.

Borrow:

- compact polling with `since_revision` and `unchanged`;
- exact approval request identities;
- a recovery fence after an uncertain local executor failure;
- validation evidence and warnings as first-class structured results;
- graceful process shutdown with bounded escalation.

Avoid:

- pinning public behavior directly to one experimental App Server protocol version without a compatibility fallback;
- shipping a private-package posture, no CI, and no public release process as v1.0.

### Codex Persistent MCP

The central insight is strong: let Codex itself own conversation persistence through `codex exec resume`, return the true session id, serialize calls per session, and keep a small repository-local pointer. A role card distinguishes the human user from the calling agent and is sent once per session. Usage data is returned when available.

The implementation also writes to `~/.codex/history.jsonl` and rewrites rollout session metadata to promote an exec session into the CLI history. Those are private storage formats rather than public bridge contracts. Working directories are not constrained to configured canonical roots, and the repository has no test suite.

Borrow:

- stable native Codex session ids when a supported interface supplies them;
- per-session serialization;
- role and audience metadata sent once rather than repeated every turn;
- returning usage data as structured accounting.

Avoid:

- modifying Codex internal history or rollout files;
- trusting an arbitrary working directory from the caller;
- making a repository pointer the sole ownership check.

### Codex session history browser

`Urus1201/codex-bridge-mcp` is useful as a narrow read-only precedent: session discovery and bounded history reading can be separated from execution. It does not solve Chat continuity, artifact adoption, or bidirectional synchronization.

Borrow only the separation between session metadata listing and bounded content retrieval. A future history adapter must use documented formats or fail softly when a Codex storage version changes.

### Baochi Codex Bridge

This project combines project inspection, test detection, tracked change records, process status, and JSONL audit events. It contains Windows and macOS setup scripts and an MCP smoke test. Its path checks and built-in secret-name denies are useful baseline defenses.

The audited commit has no license file. Some shell policy relies on regular-expression denial before executing a string through a shell, which is not a sufficient command security boundary. JSON persistence often falls back to empty state on parse failures instead of fencing recovery.

Borrow the user-facing concept of a tracked change session and cross-platform doctor scripts. Do not copy code, and do not use deny-regex shell filtering as an authorization model.

### Codex Handoff

This skill has the best repository-memory information architecture in the sample. A short index points to a current snapshot, risks, backlog, validation, decisions, workspace facts, work log, and archive. Startup reads only the minimum set. Old detail is compressed into an archive. Unknown facts are marked rather than guessed. The bootstrap script is idempotent and preserves existing unmarked files. Advisory hooks remind the agent at startup, compaction, and closeout without blocking execution.

The audited commit has no license file, and the system is convention-based: it does not bind messages to hashes, enforce transport identity, or provide an execution protocol.

Borrow:

- separate volatile snapshot from durable decisions and validation;
- minimum startup read order;
- explicit stale-state repair and archive compaction;
- advisory health checks that never become a hidden blocker.

Implement these ideas independently within the existing checkpoint and ledger format.

### Oracle and Codex with ChatGPT

The earlier audit remains valid. Oracle contributes deterministic file selection, token attribution, durable session lineage, verified browser reattachment, and careful browser leases. Codex with ChatGPT contributes canonical read-only workspace access, sensitive diff filtering, bounded execution records, OAuth and pairing discipline, and a sub-kilobyte control plane with a pull data plane.

Our v0.8 and v0.9 already adopted the relevant low-risk subset: transport-neutral mediated context, strict workspace containment, a hard token ceiling, dry-run attribution, read-only local MCP, exclusive leases, and optimistic revisions.

## Market map

| Product shape | Best examples | User benefit | Structural cost |
|---|---|---|---|
| Browser consultation | Oracle | Strong model consultation with selected files | Browser automation and reattachment complexity |
| Remote workspace agent | CodexBridge, Baochi bridge | ChatGPT can inspect and edit directly | Public endpoint, auth, shell/write risk, setup burden |
| Remote Codex supervisor | Menaje, DeepCog, Dalomeve, joseanu | ChatGPT delegates long local Codex work | Tunnel/connector availability, process lifecycle, approvals |
| Local persistent Codex proxy | madwiki | Native Codex sessions survive MCP calls | Does not use the ordinary ChatGPT Chat as durable planner |
| History/handoff memory | Urus, xu-88 | Cheap recovery across tools and windows | Convention or storage format, no full bridge lifecycle |
| Mediated ordinary-Chat bridge | This project | Uses the user's existing Chat, keeps execution local, no public service | Browser UI is the transport and must be verified and recoverable |

The last category remains underserved. This is where the project can lead instead of becoming another Developer Mode MCP server.

## v1.0 product contract

v1.0 should make five promises that are directly testable:

1. **One durable bridge, one Chat, one workspace.** A bridge has an opaque id bound to a canonical workspace fingerprint and one verified Chat identity. Switching or adopting a Chat is explicit. There is no global “latest” fallback.
2. **Resume cheaply.** A normal continuation sends only the current objective, accepted deltas, unresolved items, and requested output. Stable role, policy, and workspace facts are referenced by hashes and resent only after change or explicit refresh.
3. **No silent authority transfer.** Chat can plan and author artifacts. Codex validates, previews, adopts, applies, tests, and operates the computer. Uncertain send, response, apply, or executor state creates a recovery fence.
4. **No required public local service.** The ordinary-Chat path and local read-only STDIO MCP remain the default. A remote connector is a separately installed, explicitly enabled adapter after v1.0.
5. **Every release is verifiable.** A user can identify the source commit, artifact contents, checksums, state schema, compatibility range, tests, and upgrade path without trusting an unpublished build process.

## v1.0 backlog

### P0: required for the first public release

#### 1. Scoped Chat and workspace ownership

- Add an opaque `conversation_scope_id` derived locally from the verified Chat id and bridge id; do not persist account identifiers or the full Chat URL when a stable id is sufficient.
- Bind the scope to the canonical workspace fingerprint and current checkpoint.
- Reject cross-workspace or cross-Chat continuation with a structured `SCOPE_MISMATCH`.
- Add explicit preview/apply commands for adopting a replacement Chat after loss or deliberate migration.
- Remove any ambiguous “most recent” selection from public commands.

Acceptance: two workspaces and two Chats cannot consume or advance each other's rounds, even when commands run concurrently.

#### 2. State schema and upgrade safety

- Declare a public `state_schema_version` and supported upgrade range.
- Run read-only preflight before upgrading; create a bounded backup; validate integrity after migration; record source version, target version, tool version, timestamp, and resulting hash.
- Fence the bridge on corrupt, newer, or partially migrated state. Never replace unreadable state with an empty default.
- Add fixtures and tests for v0.8 and v0.9 upgrades, interrupted migration, duplicate ids, and rollback.

Acceptance: a copied v0.9 runtime state upgrades once, remains byte-stable on the next read, and can be restored from its backup.

#### 3. Context manifest and cost ledger

- For each outgoing packet and context response, record source, content hash, approximate tokens, reuse status, and one of `included`, `skipped`, `redacted`, or `truncated`.
- Keep a short volatile snapshot separate from durable decisions, validation, and archived history.
- Make unchanged stable context hash-addressable so a normal round references it instead of retransmitting it.
- Add cumulative totals for sent, received, protocol, duplicate, and avoided-history tokens without presenting estimates as provider billing.

Acceptance: dry run and actual send produce the same source manifest, except for transport metadata, and every omitted source has a visible reason.

#### 4. Transactional setup and diagnostics

- Add `bridge setup --dry-run` to inspect prerequisites, proposed project-local files, state location, browser path, and optional MCP configuration without writing.
- Add `bridge setup --apply` to make only the previewed, project-local changes.
- Never modify global Codex configuration automatically. Print or generate a reviewable project snippet.
- Extend Doctor with `--release` and a public-safe support bundle that contains versions, capability states, hashes, failure codes, and redacted paths, with no prompt, response, source, token, URL secret, cookie, or account data.
- Define installation success by a real local Doctor, MCP conformance call, and ordinary-Chat preflight where the environment supports it.

Acceptance: clean setup, repeat setup, partial setup recovery, uninstall, and redacted support bundle pass on Windows and macOS.

#### 5. Public release provenance

- Add `SECURITY.md`, `CONTRIBUTING.md`, `SUPPORT.md`, release policy, privacy threat model, and third-party attribution.
- Add a machine-readable release manifest containing version, exact Git commit, state schema, Node range, files, artifact hashes, validation commands, and compatibility notes.
- Produce deterministic archives, `SHA256SUMS`, and a package inventory. Since runtime dependencies are zero, state that directly and still inventory every shipped file.
- Build the public archive from a clean checkout in CI on Windows, macOS, and Linux; compare repeated builds; install and test the extracted artifact.
- Keep release creation and GitHub publication as explicit user-authorized actions.

Acceptance: a clean clone at the manifest commit recreates the same archive bytes and passes all tests, Doctor, validators, and a packaged MCP smoke test.

#### 6. Real end-to-end conformance

- Retain deterministic unit and package-copy tests.
- Add a protocol client test for initialize, tool listing, calls, invalid schemas, cancellation/timeout, and clean shutdown.
- Record a sanitized manual matrix for logged-out ChatGPT, logged-in ChatGPT, wrong Chat, uncertain send, interrupted response, recovered Chat, rejected artifact, accepted artifact, and five-round continuity.
- Add a release gate that fails when the manual matrix is stale for the release commit.

Acceptance: both automated gates and the sanitized release evidence identify the same version and commit.

### P1: high-value experience improvements

#### 7. Revision-based quiet polling

Expose `since_revision` on status and health reads. When observable state has not changed, return only status, revision, and `unchanged: true`. Keep standard and diagnostic detail levels with bounded lists and text.

This reduces repeated MCP and Codex context without hiding approvals, failures, or completion.

#### 8. Structured recovery fence

Use one recovery state machine for uncertain browser delivery, uncertain Chat response, interrupted state commit, lease loss, and local executor failure. While fenced, allow read-only inspection and explicit reconciliation; reject new rounds and writes.

The recovery response should say what is known, what is unknown, the last verified hash/revision, and the smallest safe next action.

#### 9. Operation journal and user-facing failure codes

Maintain a bounded, redacted journal for round allocation, send attempt, response harvest, adoption, artifact preview/apply, validation, migration, and recovery. Expose stable codes such as `SCOPE_MISMATCH`, `STATE_CONFLICT`, `BRIDGE_BUSY`, `UNCERTAIN_DELIVERY`, `BASE_CHANGED`, and `MIGRATION_REQUIRED` with one suggested action.

#### 10. One-time role and policy bootstrap

Send the Chat/Codex role contract, safety boundary, output schema, and stable workspace facts on initialization. Later rounds reference their hashes. Refresh only after version, policy, workspace fingerprint, or user instruction changes.

This should reduce token use while preventing role drift over a long Chat.

### P2: after v1.0

- Optional authenticated remote MCP adapter for ChatGPT Developer Mode, using named local grants and no shell/write tools by default.
- Official Secure MCP Tunnel integration when its availability and account requirements are stable enough to document accurately.
- App cards for compact status, context manifests, previews, and validation.
- Read-only native Codex session metadata adapter through supported interfaces.
- App Server executor adapter behind a compatibility layer, with CLI/STDIO fallback.
- Additional planning providers only after the ChatGPT continuity contract is stable.

## What “better” means at launch

v1.0 does not need to exceed every peer in every category. It should lead on the combination below:

| Criterion | v1.0 target |
|---|---|
| Ordinary Chat continuity | One verified Chat across rounds, explicit recovery and migration |
| Local privacy | Minimal sanitized packets, no required public endpoint |
| Authority | Chat authors; Codex verifies and applies; every transition is recorded |
| Token efficiency | Hash reuse, delta context, source manifest, quiet polling, bounded outputs |
| Crash and concurrency safety | Lease, optimistic revision, journal-before-commit, recovery fence |
| Artifact safety | Base hashes, preview/apply, protected paths, atomic placement, receipt chain |
| Public trust | Clean-clone CI, deterministic artifact, manifest, hashes, upgrades, threat model |
| Setup | Previewable, repeatable, removable, project-local by default |

CodexBridge will remain broader for direct ChatGPT editing and visual cards. Menaje will remain broader for remote supervision, App Server, and native operational UI. Oracle will remain broader as a multi-provider consultation tool. Our release can still be better for the user's stated workflow because it keeps one ordinary Chat as the high-context planner while minimizing Codex use and retaining a smaller trust boundary.

## Implementation sequence

1. Freeze the v1.0 public state and scope contracts before changing code.
2. Implement schema migration and scoped ownership first; all later features depend on them.
3. Add the context manifest and revision-based quiet reads.
4. Add setup preview/apply, release Doctor, and support bundle.
5. Add release manifest, deterministic packaging, clean-checkout CI, and upgrade tests.
6. Run the full automated and manual end-to-end matrix from the packaged artifact.
7. Review licenses, attribution, documentation, screenshots, and archive contents.
8. Create the GitHub release only after the user reviews the exact commit, archive, checksums, and release notes.

## Attribution boundary

All v1.0 implementation should remain independently written. MIT-licensed projects may be used only with the license and copyright obligations preserved if code is ever copied. No code should be copied from repositories lacking an explicit license. Design records should continue to identify the upstream base and audited peers.
